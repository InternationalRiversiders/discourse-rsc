# 校友地图、课程评价、RSDate、树洞与觅电的原生插件迁移调研

调研日期：2026-09-20。结论基于本机源码、数据库 schema、业务操作、前端组件，以及当前 Discourse 源码和官方资料。**本轮只调研，没有迁移业务、读取真实用户记录或改动线上服务。**

## 结论与实施顺序

五个项目都适合以 Discourse 原生插件为目标重构。校友地图的业务最简单；课程评价和觅电主要是结构化内容、互动和管理；树洞的关键是匿名隔离；RSDate 的关键是配对算法的等价迁移。后两项需要先做专项验证，不能仅凭页面能显示就判断迁移成功。

建议分别建设 `discourse-alumni-map`、`discourse-course-review`、`discourse-rsdate`、`discourse-whisper`、`discourse-seek`，各自拥有开关、数据库表、路由和管理权限，不依赖 RSC 插件启用。复用 RSC 已验证的原生页面、权限、事件通知和导入演练方式；不复用它的资金模型。

| 项目 | 原生迁移判断 | 相对工作量/难点（估计） | 建议顺序 |
| --- | --- | --- | --- |
| 校友地图 | 高可行性，适合首个试点 | 较小；地图 SDK、权限与位置精度 | 1 |
| 课程评价 | 高可行性，课程和导师模块都能保留 | 中到较大；聚合、双套评价、匿名评论、导入 | 2 |
| 觅电 | 高可行性，保留美食站体验 | 中到较大；图片、旧账号、审核流程、浏览器收藏 | 3 |
| 树洞 | 可行，需先验证匿名与媒体权限 | 较大；匿名身份及审核边界 | 4 |
| RSDate | 可行，算法是尚待验证的核心 | 较大且不确定性最高；Blossom 求解器、批次发布 | 5 |

顺序按迁移风险和可复用经验安排，不是工期承诺；树洞匿名和 RSDate 求解器的小型验证应提前做，正式切换放后面。未统计生产数据量、媒体体积、峰值负载，因此暂不给出精确天数。

## “原生”后的结构和能力

当前五个项目都是 Next.js/React + Prisma/PostgreSQL 的独立应用，通过 DiscourseConnect 登录；觅电的有效应用目录是 `seek-uestc/eating-app`。原生化意味着：

- 后端业务改为 Rails models/controllers/services，业务表进入论坛 PostgreSQL，带各插件独立前缀；Prisma 的规则和数据需要转换，不是直接运行 Prisma migration。
- 前端改为 Discourse 的 Ember/Glimmer `.gjs` 页面与组件。地图、卡片、评分、问卷仍能保留各自的布局，不要求改成普通主题列表。React/Next Server Actions 不能直接复制进原生页面。
- 账号、登录、分组授权使用论坛当前用户；每个页面和 API 都检查权限。旧系统缓存的角色、组名不能直接提升为论坛管理员权限。
- 定时匹配、数据导入、外部接口和通知投递由后台任务执行；计算和图片处理不能占用普通页面请求。需核对论坛现有 worker 配置与负载，不能假设新建队列后自动有消费者。
- 通知可接入论坛铃铛，点击进入对应插件页面。邮件和浏览器推送需要另做适配、用户偏好与验收，不能把自定义铃铛通知等同于自动具备全部渠道。
- 自定义模型的举报/审核可通过 `register_reviewable_type` 接入统一审核队列；需实现对应类型、权限、序列化和操作，不会因为建了表就自动获得论坛审核能力。
- 图片可接入 `Upload`/`UploadReference`，但业务对象关联、未引用文件清理、可见性都要做。`UploadReference` 防止文件失去引用，不负责内容访问授权。
- 自定义表不会自动加入论坛全文搜索、个人活动、数据导出、用户删除/匿名化流程；这些要逐项实现。尤其私密内容不应默认出现在公共搜索、用户卡片或活动页。

独立插件便于分别维护和开关，但仍共享论坛进程、数据库和部署：坏的启动代码或很重的任务可能影响主论坛。启用开关不是进程隔离，上线需要构建验收和资源限额。

官方资料确认插件可增加原生路由和管理界面，支持前端扩展；本机当前源码也确认了自定义 Reviewable、CSP 扩展和多态上传引用接口。[管理界面指南](https://meta.discourse.org/t/developing-discourse-plugins-part-5-add-an-admin-interface/31761)、[前端扩展指南](https://meta.discourse.org/t/using-plugin-outlet-connectors-from-a-theme-or-plugin/32727)、[插件接口源码](https://github.com/discourse/discourse/blob/main/lib/plugin/instance.rb)、[上传引用源码](https://github.com/discourse/discourse/blob/main/app/models/upload_reference.rb)。

## 校友地图

**现有功能。** 两个模型：本地用户与校友资料。包含自愿发布、是否展示论坛用户名、入学/毕业年份、学校专业、工作和联系方式、城市级位置、管理员隐藏；地图按缩放聚合省/城市或国家，展示人员抽屉。当前登录且具有授权组的用户才能获得地图资料。

**建议实现。** 例如 `/alumni-map` 地图、`/alumni-map/me` 编辑资料。使用专用 `alumni_profiles` 表关联论坛用户，保留高德 JS API 2.0；用 Glimmer 管理地图容器、加载与销毁，Ruby API 负责资料和地理编码。地名数据可以抽成版本化静态数据，不必为 Node 数据包保留独立后端。

**具体迁移点。**

- `isPublished`、`showForumUsername`、`hiddenAt` 是三种不同状态，不能把“已有资料”当成“同意公开”。隐藏论坛名时也不能在 API、头像或用户链接里返回真实身份。
- 当前写入会清空街道/区县细节，把坐标四舍五入到 0.25 度，并对中国城市做地理编码。导入不能重新暴露旧版详细地址；保留城市级展示，坐标系需标注并核对高德与国际地名数据的差异。
- 高德仍是外部服务。需要论坛域名的 key 配置、服务端 key、SDK 加载失败提示、必要的 CSP 域名配置、缓存及限流。高德要求在线加载 JS API，不能把整个 SDK 离线打包进插件。[高德加载说明](https://lbs.amap.com/api/javascript-api-v2/guide/abc/load)。
- 当前本人修改资料会清除 `hiddenAt/hiddenReason`。重构建议区分用户编辑和管理员恢复，避免一次编辑绕过隐藏；这是需要明确记录的行为调整。

**可增加的通知。** 资料被隐藏、恢复或需要修改。私信入口仅在用户选择公开论坛身份且符合论坛私信权限时展示。“同城有新校友”属于新增订阅功能，默认不广播位置。

**首个验收。** 普通论坛页面与地图反复切换不残留地图实例；手机抽屉可用；未认证用户拿不到资料 JSON；隐藏姓名和未发布资料不泄漏；旧资料位置精度不变细。

代码依据：[schema](/opt/alumni-map/prisma/schema.prisma)、[地图](/opt/alumni-map/components/MapView.tsx)、[公开字段](/opt/alumni-map/lib/profiles.ts)、[资料操作](/opt/alumni-map/app/actions.ts)。

## 课程 review / 选课指南

**现有功能。** 实际包含课程列表、跨学期教学班聚合、任课教师聚合页，以及独立的导师库和导师评价。共 17 个模型，涵盖多维评分、匿名评价/评论、赞踩、回复、举报、隐藏、收藏。课程来自 Excel，导师资料有学校网站导入脚本；已有 `pg_trgm` 索引。

**建议实现。** 保留课程/教师/导师入口和评分卡片，例如 `/courses`。课程、开课记录、导师、评价及互动使用插件表；老师详情仍聚合相应课程评价，导师评价保留独立业务含义。先维持现有唯一性和评分口径，后续再决定是否合并重复的评价实现。

**具体迁移点。**

- 首页课程组按“课程代码 + 名称 + 规范化教师列表”聚合；教师身份包含院系。不能只按课程名、课程代码或教师姓名合并。
- 课程评价唯一性是 `courseId + externalUserId`，导师评价是 `mentorId + externalUserId`；评分允许 0.5 步进。跨学期展示聚合不能顺手变成跨所有教学班仅保留一条评价。
- 保留课程评分、教师评分、难度、给分公平性，以及导师指导/沟通评分。赞踩不是论坛默认点赞的等价替代，需要自己的互斥规则与约束。
- 匿名评论目前有向客户端评论组件传入原始 `forumUsername` 的代码路径，显示层再写“匿名”。这是静态代码发现，未做线上抓包。迁移时用服务端白名单序列化，匿名评论不下发真实作者字段或反应用户 ID 集合；不能只改显示文字。
- Excel 和导师抓取属于导入任务；原始字段、学期和来源键要保存。可先保留离线转换器导出标准数据，原生 Rails 导入负责事务与校验，日常运行不需要旧 Next 服务。
- 普通论坛主题不能直接表达这些唯一性、评分统计与匿名评论要求。建议首版自定义数据表；以后如需公开讨论，可额外关联主题，不能为匿名评价创建会暴露作者的镜像帖子。

**通知。** 我的评价有新回复、回复被回复、内容被隐藏/恢复、举报已处理。点赞可合并通知；匿名操作者在通知中仍保持匿名。课程更新订阅是可选新增项，现有收藏不自动代表同意订阅。

**验收。** 新旧库按教学班、课程组、导师核对评价数和各维平均分；重试不能多写评价/反应；隐藏内容不计入公开统计；匿名作者不出现在 JSON 或通知；旧课程、教师和导师链接能定位新页面。

代码依据：[schema](/opt/course-review/prisma/schema.prisma)、[课程聚合](/opt/course-review/lib/course-groups.ts)、[教师聚合](/opt/course-review/lib/teachers.ts)、[互动](/opt/course-review/app/actions.ts)、[评论传参](/opt/course-review/components/ReviewCard.tsx)。

## RSDate

**现有功能。** 14 个模型，包含资料、加入/退出匹配池、学校用户组与校区规则、模块化问卷及旧版问卷、当前结果/历史结果/发布批次。后台支持预览、手工配对与清除结果、整池发布；定时任务默认按北京时间每周日 20:00 发布，可配置。

配对使用 `edmonds-blossom`，不是贪心挑最高分。先检查双向性别偏好，再组合问卷、兴趣、学校/校区、年级、自由文本向量等分数；调用开启最大配对数量优先的加权匹配。现有发布使用 PostgreSQL advisory transaction lock 和唯一周期键，配对成功的人退出池，未匹配的人保留。

**建议实现。** 资料、问卷、管理与结果页全部原生化；模型进入论坛数据库；发布迁入 Sidekiq 定时任务。现有 embedding 可按 JSONB 保存，没有必须安装向量数据库的前提。外部 embedding 调用作为可选后台任务，保留模型与版本，失败时明确降级。

**最大待验证项：求解器。** 当前依赖是 Node 包，不能在 Rails 里直接 `require` 使用。完整原生目标应选择经验证的 Ruby 实现或移植求解器；用小规模穷举和旧求解器做对照，比较最大配对数量、总权重、兼容条件和同分稳定性。暂未验证合适的 Ruby 实现，也未执行移植。不能用贪心或只适合男女两组的简单二分匹配替代当前允许“不限”等偏好的行为。[当前求解器项目](https://github.com/mattkrick/EdmondsBlossom)。

如果纯 Ruby 求解性能不满足目标人数，可以由插件调用隔离的计算进程，但那是保留计算组件的折中方案，应明确说明，不称作完全原生。当前没有生产池规模和性能样本，不能断言必须或不需要这一折中。

**其他迁移点。**

- 保留问卷修改后旧答案失效的判定、必答模块完成条件、学校组规则、手工发布与周期发布的差异。
- 保留锁、周期唯一约束、双向结果、退出池和历史的一致性；发布重试只通知一次。计算可从快照执行，落库前再验证参与状态，避免计算期间退出的人仍被配对。
- 原始答案和择偶资料仅本人/授权管理人员可读；对方可见字段按现有结果页规则处理。不加入公开用户资料、活动或全文搜索。相同维度但不同模型的 embedding 也不能直接混算。
- 旧版问卷表和模块问卷表同时存在，迁移不能只导入当前活跃模型。历史结果和发布周期也必须保留，以免重复发布。
- 当前源码的候选构造未见历史配对排除条件；“不重复匹配旧对象”若要加，应作为新规则讨论，不应误称已有能力。

**通知。** 新一期结果已发布、此次未匹配、问卷变更需补填。铃铛只给中性提示，点击鉴权后查看资料；不把答案、性别偏好或对方详情写进锁屏可能展示的文本。可以提供私信入口，但迁移本身不自动替用户建立私聊。

**验收。** 固定样本与旧算法对照、奇数池/无可用边/同分/向量缺失、批次重试、手工发布并发、时区、退出池一致性，以及目标池规模下的运行时间和内存。

代码依据：[schema](/opt/rsdate/prisma/schema.prisma)、[完整匹配与发布](/opt/rsdate/lib/matching.ts)、[历史与手工配对](/opt/rsdate/lib/match-results.ts)、[向量](/opt/rsdate/lib/embeddings.ts)、[时间规则](/opt/rsdate/lib/matching/schedule.ts)。

## 树洞 / Whisper

**现有功能。** 8 个模型，包含匿名主贴/回复、图片、同帖“洞主/匿名 A/B”等别名、赞踩、举报、隐藏/删除/恢复、独立禁言字段、站内通知，以及管理员实名查看的理由与审计。当前公开给授权读者的审计包含管理员、理由和时间，不公开被查看者真实身份。

**建议实现。** 专用树洞数据表与页面，例如 `/whisper`。真实作者关联保留在受保护的后端字段，返回公开内容时只提供该树洞内的别名；匿名映射独立存储，不以全站用户 ID 作为前端识别符。匿名内容不进入主账号公开活动。

Discourse 原生匿名模式使用关联的匿名账号，账号会在一定条件下复用，它不等价于当前每个树洞内的 A/B 身份。因此直接开启匿名模式或隐藏普通帖用户名，均不能直接实现现有语义。[匿名账号实现](https://github.com/discourse/discourse/blob/main/app/services/anonymous_shadow_creator.rb)。

**具体迁移点。**

- 匿名别名需要按旧帖的可见评论顺序核对并固化迁移映射，避免隐藏某条回复后其他人的 A/B 全部变化；不同帖不能用相同公开标识串联真实用户。
- 查看身份必须单独授权、填写理由、写审计，再展示结果；常规审核列表不直接列真实作者。数据库/服务器管理人员仍能接触底层数据，这是业务匿名而非对系统管理者的不可追踪性。
- 回复和点赞通知可进入论坛铃铛，但发送者字段不能套用 RSC 的真实 `display_username`；使用“洞主/匿名 A”等业务身份。私信、提及、引用预览也必须遵守同一边界。
- 举报可接入自定义 Reviewable，审核内容与身份解密分离。保留树洞内部禁言状态，不直接把它升级成全论坛封禁。
- 图片需要单独验证。旧上传文件名含本地作者 ID，旧图片路由没有登录校验；新站若要求校友可见，必须同时保护图片原件/缩略图，单保护帖子 API 不够。导入时重命名并保存私有映射，核对元数据、上传者序列化及缓存，不能把树洞图片当普通公开附件。
- 旧 `publicCode`、评论父子关系、已读通知、举报与身份查看审计都要保留。历史通知迁移不重新大批推送。

**验收。** 分别用游客、未认证用户、普通校友、洞主、匿名回复者、审核者测试；查看页面、JSON、通知、图片地址、分享预览、用户活动和导出结果；确认普通内容审核不能绕过身份查看审计。

代码依据：[schema](/opt/whisper/prisma/schema.prisma)、[匿名别名](/opt/whisper/lib/anonymous.ts)、[公开字段](/opt/whisper/lib/treehole.ts)、[审计与通知](/opt/whisper/app/actions.ts)、[上传](/opt/whisper/app/api/upload/route.ts)、[图片访问](/opt/whisper/app/uploads/[filename]/route.ts)。

## 觅电 / Seek UESTC

**现有功能。** 11 个模型，包含店铺筛选、区域与价格、店铺详情/图库、评分评论与回复、菜品与点赞、推荐、收藏、分享图、新店申请、店铺资料修改审核、贡献记录、营业/关闭状态、关于页及评论。现有访客可浏览美食首页，写操作走登录权限。

**建议实现。** 例如 `/food` 保留店铺卡片、详情图库、菜品、评论标签和手机底部操作。店铺/菜品/修改提案用专表，首版评论也保持业务表以保留评分、图片与回复关系；后台审核可接入 Reviewable。以后需要主论坛讨论时可关联主题，不必先把全部旧评论转换为 Posts。

**具体迁移点。**

- **账号不能按旧 users.id 对号入座。** 本地用户是自增 BigInt，`github_id` 列已被映射为 `providerUserKey`，现在可能存 `discourse:<论坛 ID>`，同时还要处理旧 GitHub/dev 数据。已有合并工具不代表所有旧账号都已合并。对已验证的论坛关联建立映射；未匹配的历史作者保留来源归属，不能仅凭用户名把内容绑定给论坛用户，更不能沿用旧角色授予管理员权力。
- **收藏在 `localStorage['eating:favorites']`，数据库里没有收藏表。** 迁移到论坛域名后无法直接读旧子域名的存储。可保留旧页的一次性导出/登录导入入口，或给用户下载再导入；只迁数据库会漏掉收藏。原生版本建议存入账号，获得跨设备同步。
- 每日推荐也是浏览器端种子随机，不需要额外算法服务；可以先保留现有交互。分享图的 `html2canvas` 要适配新 DOM、字体和图片跨域，不是后端迁移难点。
- 店铺、菜品和评论图片既有仓库文件又可能来自持久卷，要做完整媒体清单、哈希/可读性校验、上传引用和旧路径映射，不能只复制数据库中的文件名。
- 店铺原始评分参与平均值，回复评分不计入店铺总分；必须保留这一口径，不能仅按迁移后的所有评论重新求平均。
- 修改申请包含提交前快照和完整变更，审批时需要版本/冲突检查与幂等，避免后批准的旧提案覆盖别人已通过的更新。公开贡献历史和审核人归属要保存。

**通知。** 新店申请通过/驳回、资料修改通过/驳回、评论被回复、菜品被点赞；可选添加收藏店铺停业/恢复订阅，明确由用户选择。

**验收。** 店铺/菜品/评论/图片和赞数对账，旧账号映射、同一提案重复审批、并发修改冲突、评论评分口径、收藏跨域导入，以及首页筛选/推荐/图库/分享在移动端的体验。

## 共用的数据迁移与上线约定

1. 从旧库一致性快照导出，文件只含迁移所需业务数据；媒体另做清单。先统计行数、关联、无法匹配账号和冲突，不直接覆盖论坛数据。
2. 本机 DiscourseConnect provider 源码把论坛 `current_user.id` 写为 `external_id`。前四个项目可据此建立映射，但仍需核实历史来源、缺失用户、合并/改名记录；觅电额外处理 provider 前缀和独立本地 ID。
3. 新表使用自己的数值主键，同时保留 `legacy_source + legacy_id` 唯一映射，支持旧 CUID/BigInt 和旧 URL。不要把不同库的本地用户 ID 当成论坛 user_id。
4. 在隔离论坛先执行可回滚演练，校验引用和业务统计；真实导入幂等可重试，不重发历史通知、不重新执行历史配对、不公开原本私密的数据。
5. 媒体完成引用和可读性检查，旧链接逐类映射。纯页面可按计划重定向，图片需要保持其访问控制；旧写入 API 不能随意重定向为新写入。
6. 每次只切换一个应用的写入。停旧写入后做最终同步，核对通过再开放新入口；RSDate 停旧 cron，避免双边发布。旧站短期只读，原库和媒体保留用于核对。
7. 切换后已有新写入时，不能简单重开旧站写入作为回滚，必须先处理新数据回流或恢复方案。开关插件也不能让待执行任务继续产生业务变化。

完成标准包括：功能和统计口径一致、旧 URL/媒体有效、权限与匿名语义保留、通知只投递一次、手机关键流程可用、五个插件与 RSC 同时安装不冲突。自定义表进入论坛数据库后会受论坛数据库备份覆盖，但媒体、外部配置和恢复后的插件版本仍需一并验收。
