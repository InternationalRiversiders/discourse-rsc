# 原生插件重构设计

用户已确定采用完整原生插件方案。本次重构以当前业务和资产连续性为基础，重新组织实现。棋牌游戏已明确排除，赛事预测保留。当前不改变现有业务规则，不重置用户资产。

**最终运行形态**

- 一个 `discourse-rsc` 插件仓库，入口为 `plugin.rb`。
- Ruby 服务在 Discourse 内运行；资金、红包、订单等独立业务表使用 `discourse_rsc_` 前缀。
- 直接使用论坛用户 ID、登录态、用户组和 Guardian 权限。
- Ember/Glimmer 实现钱包、交易页面和论坛内打赏；逐步吸收原主题组件。
- Jobs 承担结算、重试和定时检查；长连接行情接入作为可重启、有明确生命周期的独立后台执行单元设计，仍属于插件部署，不在网页请求进程中启动无限循环。
- 原生站内通知与业务事件关联；邮件、Web Push 和自有 App 系统推送分别验收。

**模块边界**

| 模块 | 职责 | 不应承担的职责 |
| --- | --- | --- |
| Accounting | 金额、账户、成对分录、并发锁、请求幂等、审计 | 获取行情或处理交易规则 |
| Wallet | 转账、账户管理、限额、管理员发行 | 直接更新其他模块的业务状态 |
| Forum rewards | 打赏、每日奖励、帖子权限、奖励规则 | 独立维护另一份余额 |
| Red packets | 固定/随机分配、托管资金、领取、结束、退款 | 在通知发送成功之后才结算 |
| Exchange | 市场、报价、订单状态、持仓、保证金、条件触发、强平 | 将所有功能再次塞进一个巨型服务文件 |
| Sports | 赛事预测、赔率、到期结算 | 绕过账本扣款或发奖 |
| Notifications | 展示业务结果、去重、重试与偏好 | 推测余额变化代表什么业务事件 |
| Migration | 旧库导入、历史追溯、金额核对、切换报告 | 在导入过程中悄悄修改产品规则 |

**资金模型**

`Account` 保存当前余额；`Journal` 表示一次已经提交的业务记账；`Entry` 是该记账涉及的账户增减；`Event` 保存业务结果待投递的通知。

每笔 Journal 的 Entry 总和为零。管理员发币对应系统发行账户负向变动和用户账户正向变动，因此可以解释币从哪里产生。红包与交易冻结资金通过托管账户表达，不能只用不透明的“可用余额修正值”。具体保证金和损益账户在交易阶段定义。

金额保留旧系统 18 位精度，转账/打赏入口限制两位小数。存储上限为 78 位最小单位整数，旧库导入必须检查是否超限。重构不应擅自将全部资金取整到分。

记账、余额和通知事件必须在同一 PostgreSQL 事务中写入。通知通过后续任务创建，其失败不会撤销已经提交的资金交易。创建通知和标记事件已投递也使用一个事务。

所有资金操作具有稳定的请求编号；重复请求返回原结果，重用编号但改变金额/对象/业务上下文必须失败。账户锁按 ID 顺序获取，避免 A 转 B 与 B 转 A 的锁顺序相反。限额在账户锁内检查，防止同时操作绕过额度。

当前数据库约束保护 journal 收支平衡与历史不可变，余额变更集中在 Ledger 服务。后续增加独立对账任务，定期核对账户快照与分录汇总；不要把“有数据库约束”理解为已经完成全部财务一致性验证。

用户或帖子被删除后，资金审计记录仍需保留。删除、匿名化、帖子不可见后的通知处理，必须在正式上线前分别定义。冻结账户也需区分“禁止主动交易”和“允许退款/风险结算”，现有基础版严格拒绝冻结账户变动，尚不能替代完整冻结规则。

**迁移顺序与验收**

| 阶段 | 交付内容 | 进入下一阶段的条件 |
| --- | --- | --- |
| 1：原生账本基础 | 插件加载、数据库迁移、精确金额、幂等、账户锁、转账/打赏/发币接口、通知事件 | 并发、重放、事务回滚、原生权限与通知测试通过 |
| 2：社区钱包 | 钱包 UI、原打赏组件、红包、每日奖励、发行/冻结/豁免后台、通知跳转 | 与旧规则逐项对照，浏览器和手机界面验收 |
| 3：交易所 | 行情适配器、订单状态机、持仓保证金、条件单、延迟成交、爆仓事件 | 复现旧系统关键样本；零现金爆仓不漏报；行情失败不重复成交 |
| 4：赛事预测 | 赛事数据、预测、结算、资金托管 | 断线/重启/重复任务不会重复结算 |
| 5：历史与切换 | 可重复导入、旧新资产对账、切换脚本和回滚演练 | 无未解释差额，所有写入口切换到同一个新账本 |

阶段 1 的账本基础已实现；阶段 2–4 已有隔离试用实现，完整数据源与规则迁移仍待完成。这个阶段划分是施工顺序，不意味着应在各阶段分别迁移生产余额。

旧系统可以继续提供服务，新插件在隔离数据上开发和验收。不能把生产转账迁到 PostgreSQL，却让生产交易继续修改 SQLite 中的同一笔钱。正式资金切换应在相关消费模块全部就绪后统一进行；如果需要更早切换，必须单独设计过渡调用协议。

**旧数据迁移要求**

先从一致性快照读取旧 SQLite，并记录版本、导出时间与校验和。不得将不断变化的线上表逐个导出后拼成一个资金快照。

必须核对的对象包括现金余额、冻结状态、临时限额豁免、未结清红包、分配与领取记录、持仓保证金、未完成订单及资金预留、未结算赛事预测资金、奖励发放记录和原始历史流水。仅导入当前钱包余额不足以保留资产。

旧系统并非完整复式账本，不能假装每条历史记录都能直接变成完整的新式 Journal。建议保留带原始主键的旧历史档案，并通过明确的期初资产分录引入当前状态；可配对的历史业务另作索引，避免期初余额与历史流水重复入账。方案须在实际旧库审计后固定。

导入不能给用户补发所有历史通知。余额按最小单位逐户比对，红包/保证金/冻结金额单独汇总验证。用户 ID 不存在、重复导入、无法解释的差额均应生成阻断报告，不能静默忽略。

切换时停止旧写入与旧后台结算，导出最终快照，导入、核对，再统一开放新写入。新系统产生交易后，不能简单恢复旧库文件当作回滚；需要停止写入、导出新交易并设计反向同步或明确恢复点。

**现有代码中需要保留或修正的细节**

- 普通转账补充请求幂等，打赏继续保留已有幂等语义。
- 红包到期状态、退款和事件要原子提交；异常抛出路径不能把部分更新意外回滚。
- 爆仓事件由订单结算生成，不能只依赖现金流水；零现金退回也必须通知。
- 私有分类和帖子通过 Guardian 检查权限；不沿用“只查询帖子存在”的做法。
- 奖励仍以北京时间业务日结算，活动规则变化应另行确认。
- 报价时间、收到时间和下单时间分开保存，保留延迟成交和报价过期规则。
- 前端的请求重试、服务端任务重试和通知重试分别验证，不能共用一个模糊的成功标志。
